# Spec: メモ・写真・録音から日報/月報を作る機能要件

## 背景

日々の作業では、あとで日報や月報にまとめたい情報が小さな単位で発生する。
たとえば作業メモ、気づき、出来事、写真、録音、文字起こしなどは、その場で残せないと失われやすい。

この仕様では、ローカル環境でそれらを蓄積し、必要な記録を見つけ、日報や月報に再利用できる状態を定義する。
実装方式を固定しすぎず、まずはユーザー体験、保存したい情報、MVP の境界を明確にする。

## 目的

- どの情報を入力、保存、検索、編集できる必要があるかを明確にする
- email とパスワードによるログインと権限制御の要件を明確にする
- 写真、録音、文字起こしをどの範囲で扱うかを整理する
- 日報、月報生成に必要な集計、抽出、編集フローを定義する
- ローカル利用を前提にした保存、プライバシー、バックアップ方針を整理する
- MVP で実装する範囲と後続 Issue に分ける範囲を判断できるようにする

## 対象ユーザー

- 自分の作業内容や気づきを日々ローカル環境で記録したいユーザー
- 記録したメモ、写真、録音、文字起こしから日報や月報を作りたいユーザー
- 外部サービスに全ての記録を預けず、自分の端末上でデータを管理したいユーザー

## スコープ

### やること

- email とパスワードでログインできるようにする
- 初回起動時に admin ユーザーを作成できるようにする
- 設定画面で複数アカウントを登録、権限管理できるようにする
- admin/user の 2 権限を定義し、画面と操作の制御を行う
- ユーザーごとに記録、日報、月報の参照範囲を分離する
- テキストメモ、写真、録音、文字起こしを記録として保存する
- 記録に日付、タグ、カテゴリ、関連プロジェクトなどのメタ情報を付与する
- 記録を日付別、タグ別、種類別、キーワードで探せるようにする
- 当日の記録から日報候補を抽出し、ユーザーが編集して Markdown として出力できるようにする
- 指定月の記録や日報から月報候補を作り、元記録へ戻れるようにする
- ローカル保存、バックアップ、プライバシー、外部 API 利用時の注意点を定義する

### やらないこと

- 複数ユーザーでの共同編集
- SSO や外部 ID プロバイダ連携
- クラウド同期を必須にしたデータ管理
- 外部カレンダー、タスク管理、勤怠システムとの自動連携
- 写真や音声の高度な自動分類、顔認識、話者識別
- 生成された日報や月報を外部サービスへ自動投稿する機能

## ユースケース

1. UC01: ユーザーは作業中に気づいたこと、作業メモ、出来事をすぐに記録する
2. UC02: ユーザーは写真だけの記録を作成する、またはメモに写真を添付して文脈を残す
3. UC03: ユーザーは会話や思考メモをアプリ内で録音し、必要に応じて文字起こしを保存する
4. UC04: ユーザーは保存済み記録を日付、タグ、種類、キーワードで検索して再利用する
5. UC05: ユーザーは当日の記録を見返し、日報の下書きを作成する
6. UC06: ユーザーは指定月の記録や日報を集約し、月報の下書きを作成する
7. UC07: 初回起動時に管理者は admin アカウントを作成し、運用を開始する
8. UC07: 管理者は設定画面で user アカウントを追加、更新、停止する
9. UC07: ユーザーは自分の記録とレポートだけを閲覧できる
10. UC08: 管理者は外部 AI プロバイダ、モデル、API キーを設定する
11. UC09: ユーザーは日報/月報テンプレートを設定画面から編集する

## 機能要件

### 認証と認可

ログインは email とパスワードで行い、認証状態は JWT ベースのトークンで管理する。
初回起動では admin ユーザーを 1 件作成してから利用を開始する。

必須要件:

- ログイン時に email とパスワードを検証できる
- 初回起動時のみ admin 登録フローを表示する
- 権限は `admin` と `user` の 2 種類のみとする
- `admin` は設定画面で複数アカウントを登録、編集、停止できる
- `admin` はアカウント作成時に初期パスワードを設定できる
- `admin` は必要に応じて user のパスワードを再設定できる
- `admin` はアカウントを停止できる
- 停止アカウントはログインできない
- 停止アカウントの既存データは削除せず保持する
- `user` はアカウント管理機能へアクセスできない
- 記録、日報、月報は `ownerUserId` で管理し、本人以外は参照不可とする
- API と画面の両方で認可チェックを行う

セキュリティ要件:

- パスワードは平文保存しない
- パスワードは 8 文字以上を必須とし、文字種の組み合わせは必須にしない
- パスワードハッシュは計算コストを持つ方式を使う
- 認証失敗ログを記録し、過剰試行時の制限を設ける
- JWT は有効期限を持つ
- ログアウト時は発行済みトークンを失効できる
- API は Authorization ヘッダーの Bearer トークンを検証する
- アカウント管理操作は監査ログを残す
- パスワード再設定操作は監査ログを残す

### 記録の基本データ

記録は、テキスト、写真、音声、文字起こしをひとまとまりで扱える単位とする。

保存する主な項目:

- ID
- ownerUserId
- 作成日時
- 更新日時
- 対象日
- タイトル
- 本文
- 種類
- タグ
- カテゴリ
- 関連プロジェクト
- 添付ファイル一覧
- 文字起こし本文
- 日報または月報で利用済みかどうか
- 元記録への参照

種類の例:

- memo
- photo
- audio
- transcript
- daily_report
- monthly_report

### テキストメモ

ユーザーはテキストメモを作成、編集、削除できる。
メモ本文は Markdown を許容し、日報や月報へ転記しやすい形式で保存する。

必須要件:

- 本文を保存できる
- 対象日を設定できる
- タグ、カテゴリ、関連プロジェクトを付与できる
- 後から内容とメタ情報を編集できる
- 削除時は添付ファイルとの関係を確認できる

### 写真

ユーザーは写真ファイルを写真だけの単体記録として保存できる。
また、既存の記録に写真を添付して、記録本文から参照できる。

必須要件:

- 写真ファイルをアップロードできる
- 写真だけの単体記録を作成できる
- 写真にタイトル、対象日、タグを付与できる
- 添付した写真をプレビューできる
- 写真に説明文を付与できる
- 写真を記録から削除できる
- 削除時にファイル本体を消すか、参照だけ外すかを判別できる

MVP では、画像編集や自動補正は扱わない。

### 録音

ユーザーは音声を録音し、音声だけの単体記録として保存できる。
保存した音声は後から再生でき、必要に応じて文字起こしの元データとして扱う。

必須要件:

- 録音を開始、停止できる
- 外部で作成済みの音声ファイルをアップロードして取り込める
- 音声ファイルを保存できる
- 音声だけの単体記録を作成できる
- 保存済み音声を再生できる
- 音声にタイトル、対象日、タグを付与できる
- 音声ファイルの保存場所を記録から参照できる

MVP では、音声編集、ノイズ除去、話者識別は扱わない。

### 文字起こし

ユーザーは録音内容の文字起こし結果を保存、編集できる。
文字起こしは手動入力、外部 API、ローカルモデルのいずれでも登録できるようにする。

必須要件:

- 音声記録に文字起こし本文を関連付けられる
- 文字起こし本文を編集できる
- 文字起こしの作成方法を保存できる
- 文字起こしの作成日時を保存できる
- 元音声へ戻れる参照を保持する

文字起こしの作成方法:

- manual
- local_model
- external_api

外部 API を使う場合は、送信される音声やテキストの範囲をユーザーに明示する。

### 外部 AI プロバイダ設定

外部 AI を使った文字起こし、日報、月報の補助機能を後から有効化できるように、設定画面でプロバイダ、モデル、API キーを管理できるようにする。

対応プロバイダ:

- OpenAI (ChatGPT)
- Anthropic (Claude)

必須要件:

- `admin` は設定画面で外部 AI プロバイダを有効/無効にできる
- `admin` は OpenAI と Anthropic の両方を登録できる
- `admin` はプロバイダごとにモデル ID を指定できる
- `admin` はプロバイダごとに API キーを登録、更新、削除できる
- API キーは安全に保管し、平文で再表示しない
- API キーはサーバー側でのみ復号し、ブラウザへ返さない
- API キーの表示は末尾数文字などのマスク済み表示に限定する
- 外部 API へ送信するデータ種別と範囲を、実行前にユーザーへ明示する
- 外部 API を使わず、手動入力だけでも運用できる

API キーの保存方針:

- SQLite には暗号化済み API キーとマスク済み表示名だけを保存する
- 暗号化鍵は `data/` 配下やリポジトリに保存せず、環境変数または OS の秘密情報ストアから読み込む
- 接続テスト時も API キーの平文をログに出力しない
- 設定更新、削除、接続テストは監査ログに残す

### 一覧と検索

ユーザーは保存した記録を見つけやすい形で一覧、検索できる。

必須要件:

- 日付別に表示できる
- タグ別に表示できる
- 種類別に表示できる
- キーワード検索できる
- 写真、音声、文字起こしを含む記録を検索対象にできる
- 検索結果から元記録を開ける
- ログイン中ユーザー自身の記録だけを結果に含める

検索対象:

- タイトル
- 本文
- タグ
- カテゴリ
- 関連プロジェクト
- 写真の説明文
- 文字起こし本文

MVP では全文検索エンジンの高度なランキングは必須にしない。
単純な部分一致、日付、タグ、種類の絞り込みを優先する。

### 日報生成

ユーザーは当日の記録から日報の下書きを作成できる。
生成結果は自動確定せず、ユーザーが編集して保存する。

必須要件:

- 対象日を指定できる
- 対象日の記録を候補として抽出できる
- 候補を選択、除外できる
- 作業内容、気づき、課題、次のアクションに整理できる
- 設定画面で編集した日報テンプレートを下書き生成に利用できる
- 生成結果をユーザーが編集できる
- 設定済みの OpenAI (ChatGPT) または Anthropic (Claude) を使って下書き生成を補助できる
- 外部 AI を使う場合は送信対象の記録本文、写真説明文、文字起こし本文を実行前に確認できる
- Markdown として保存、出力できる
- 日報から元記録へ戻れる
- 本人が所有する記録のみ日報候補として利用できる

日報の構成例:

- 日付
- 作業内容
- 気づき
- 課題
- 次のアクション
- 参照した記録

MVP では、自動要約の品質よりも、候補抽出、送信前確認、編集、Markdown 出力を優先する。

### 月報生成

ユーザーは指定月の記録や日報を集約し、月報の下書きを作成できる。
月報は日報よりも期間の振り返りに寄せた構成とする。

必須要件:

- 対象月を指定できる
- 指定月の記録と日報を抽出できる
- 主な成果、継続課題、学び、次月の予定に整理できる
- 設定画面で編集した月報テンプレートを下書き生成に利用できる
- 生成結果をユーザーが編集できる
- 設定済みの OpenAI (ChatGPT) または Anthropic (Claude) を使って下書き生成を補助できる
- 外部 AI を使う場合は送信対象の日報本文、記録本文、写真説明文、文字起こし本文を実行前に確認できる
- Markdown として保存、出力できる
- 月報から元の日報または記録へ戻れる
- 本人が所有する日報と記録のみ月報候補として利用できる

月報の構成例:

- 対象月
- 主な成果
- 継続課題
- 学び
- 次月の予定
- 参照した日報
- 参照した記録

MVP では、月報は保存済み日報を主な入力にする。
日報がない日の記録も追加候補として参照できるようにする。

### レポートテンプレート設定

ユーザーは設定画面で、自分の日報テンプレートと月報テンプレートを編集できる。
テンプレートは下書き生成の構成と初期本文に利用し、生成済みレポートには利用時点のテンプレート内容をスナップショットとして残す。

必須要件:

- ユーザーは自分の日報テンプレートを作成、編集、削除できる
- ユーザーは自分の月報テンプレートを作成、編集、削除できる
- テンプレート本文は Markdown とプレースホルダーを許可する
- テンプレート種別は `daily_report` と `monthly_report` とする
- 種別ごとに既定テンプレートを 1 件指定できる
- 初期状態ではシステム既定テンプレートを利用できる
- 他ユーザーのテンプレートは参照、編集できない
- テンプレート変更後も、保存済み日報/月報の本文は自動変更しない
- 日報/月報保存時に、利用したテンプレート ID とテンプレート本文スナップショットを保存する

テンプレートで利用できるプレースホルダー例:

- `{{targetDate}}`
- `{{targetMonth}}`
- `{{records}}`
- `{{dailyReports}}`
- `{{sections}}`

## 保存データと添付ファイル

### 保存方針

ローカル利用を前提に、メタデータと本文は SQLite に保存し、写真や音声はファイルとして分けて保存する。
検索や集計に使う項目は、後から FTS5 などで参照しやすい構造にする。

推奨する保存単位:

- 記録メタデータ
- 記録本文
- 添付ファイル
- 生成済み日報
- 生成済み月報
- レポートテンプレート

保存場所の例:

```text
data/
  records/
  reports/
  attachments/
    images/
    audio/
  backups/
```

各記録は添付ファイルの相対パスを保持する。
ファイル移動やバックアップをしやすくするため、絶対パスに依存しない。

添付ファイル ID と保存ファイル名:

- 添付ファイル ID は UUID v7 とする
- 保存ファイル名は `<attachmentId>.<ext>` とする
- 元ファイル名はメタデータとして SQLite に保存する
- 拡張子は検証済み MIME type と対応するものだけを許可する
- 記録や添付ファイルの参照には保存ファイル名ではなく添付ファイル ID を使う

### バックアップ

最低限、ユーザーが `data/` 全体をコピーすれば復元できる構成にする。

必須要件:

- データと添付ファイルの保存場所を明示する
- バックアップ対象ディレクトリを明示する
- 書き込み中の破損を避ける
- 削除前に確認できる

MVP では、自動バックアップは必須にしない。
ただし、後続でバックアップ世代管理を追加できる構成にする。

### プライバシー

写真、音声、文字起こしには個人情報や機密情報が含まれる可能性がある。
ローカル保存を基本とし、外部 API を使う場合は明示的なユーザー操作を必要とする。

必須要件:

- ローカルに保存されるデータの場所を説明する
- 外部 API に送信されるデータの種類を説明する
- 外部 API 利用の有効/無効を選べる
- 外部 API を使わずに手動入力で運用できる
- API キーを平文保存、平文表示、ログ出力しない
- 写真、音声、文字起こしを削除できる
- アカウント情報に対する操作権限を `admin` のみに制限する
